# Electron 整包升级：从 1.0.0 到 1.0.1 的学习记录

本文按照本次实际操作顺序，解释每一步的命令、文件变化和代码调用。示例基于当前项目、macOS arm64、electron-builder 26.15.3 和 electron-updater 6.8.9。

你已确认完成：1.0.0 打包、发布、服务器启动、安装启动、同版本检查，以及 1.0.1 下载完成。你尚未反馈此次点击安装后的结果；本文将原生安装的预期行为与此前示例验证中出现的签名错误分别说明。

## 一、先认识整套流程中的角色

本例更新整个桌面应用：Electron 运行时、Main 主进程、Preload 和三个前端应用一起打包。两个版本先只改变版本号，便于观察升级链路。

| 文件或模块 | 职责 | 执行时机 |
|---|---|---|
| `scripts/release-demo.mjs` | 编译代码，构建指定版本的安装包和清单 | 开发者构建版本时 |
| `electron-builder.yml` | 声明应用身份、打包内容、目标和更新地址 | 打包时读取 |
| `scripts/publish-demo.mjs` | 将产物复制到服务器目录，切换最新版本清单 | 开发者发布版本时 |
| `scripts/update-server.mjs` | 通过 HTTP 提供服务器目录中的文件 | 实验期间保持运行 |
| `electron/main/updates/UpdateService.ts` | 菜单交互、更新状态、检查、下载和安装编排 | 客户端主进程运行时 |
| `electron-updater` | 读取配置、请求清单、比较版本、下载校验、对接原生更新 | 更新服务调用时 |

三个脚本都运行在终端里，不在客户端里执行。本地服务器只返回文件，不比较客户端版本，也不负责安装。

```text
源码 → 编译 → release/版本/ 中的安装包、ZIP、清单
                        ↓ 发布脚本复制
                  update-server/ 目录
                        ↓ 本地 HTTP 服务器
                  http://127.0.0.1:8088
                        ↑ 请求清单与 ZIP
                  安装后的 Electron 客户端
```

## 二、第一步：构建 1.0.0

在项目根目录执行：

```bash
cd /Users/hongnny/github/electron-app
npm run release:demo -- 1.0.0 --unsigned
```

`npm run` 后面的 `--` 把后续参数交给脚本；脚本通过 `process.argv[2]` 取得 `1.0.0`，通过参数列表判断是否使用 `--unsigned`。

### 2.1 先编译，再打包

`release-demo.mjs` 先执行：

```js
run(['run', 'build'])
```

项目的 build 将 Main、Preload 编译到 `dist-electron/`，将三个 Vite 前端编译到 `dist/apps/`。这些是编译输出，还不是可以分发的安装包。

随后调用 electron-builder，核心参数是：

```js
const args = [
  'exec', '--', 'electron-builder',
  '--publish', 'never',
  `--config.extraMetadata.version=${version}`
]
```

- `--publish never`：只生成产物，发布由另一个脚本负责。
- `extraMetadata.version`：把产物内的 `package.json.version` 覆盖为 1.0.0；源码 package.json 保持原版本。
- macOS 使用当前机器架构构建；`--unsigned` 明确关闭应用代码签名。

安装后的 `app.getVersion()` 读取产物版本，所以显示 1.0.0，而不是源码里的 0.2.0。

### 2.2 打包配置决定包里有什么

`electron-builder.yml` 的核心内容：

```yaml
appId: com.example.electron-update-learning
productName: Electron Update Learning
files:
  - dist/**/*
  - dist-electron/**/*
  - package.json
  - '!**/*.map'
directories:
  output: release/${version}
publish:
  provider: generic
  url: http://127.0.0.1:8088
mac:
  target:
    - zip
    - dmg
```

两个版本保持相同的应用身份和名称。builder 收集编译文件和生产依赖，打成完整应用。DMG 用于首次安装，ZIP 供本例的 macOS 自动更新使用。

输出大致为：

```text
release/1.0.0/
├── mac-arm64/Electron Update Learning.app
├── Electron Update Learning-1.0.0-arm64.dmg
├── Electron Update Learning-1.0.0-arm64-mac.zip
├── *.blockmap
├── latest-mac.yml
└── demo-build.json
```

`blockmap` 用于差分下载相关机制；本地教学服务器提供完整文件下载，不实现 Range 请求，不要求此次实验走差分路径。`demo-build.json` 只是构建记录，不是更新器读取的清单。

## 三、第二步：发布 1.0.0，启动本地服务器

```bash
npm run publish:demo -- 1.0.0
npm run updates:serve
```

### 3.1 发布是把产物放到服务器目录

`publish-demo.mjs` 从 `release/1.0.0/` 复制 ZIP、DMG、blockmap 到 `update-server/`。

清单最后发布：先复制为临时文件，再重命名替换 `latest-mac.yml`。这样客户端看到新清单时，清单引用的下载文件已经存在；不会读到复制到一半的清单。

```text
release/1.0.0/ → update-server/
```

构建完成不等于发布完成。客户端只访问服务器目录，不访问 `release/`。

### 3.2 服务器只做文件映射

`update-server.mjs` 的文件根目录是：

```js
const root = path.resolve('update-server')
```

监听地址为 `127.0.0.1:8088`，只供本机实验。收到 URL 后映射到磁盘文件，再通过文件流返回：

```text
GET /latest-mac.yml
    → update-server/latest-mac.yml

GET /Electron%20Update%20Learning-1.0.0-arm64-mac.zip
    → update-server/Electron Update Learning-1.0.0-arm64-mac.zip
```

```js
createReadStream(file).pipe(response)
```

脚本检查路径范围和文件类型，只提供 GET/HEAD；找不到文件返回 404。`Cache-Control: no-store` 方便实验中及时读取切换后的清单。

保持服务器终端运行，另开终端检查：

```bash
curl http://127.0.0.1:8088/latest-mac.yml
```

你已看到 `version: 1.0.0`，说明服务器能返回旧版清单。

## 四、第三步：安装并启动 1.0.0

1. 打开 `release/1.0.0/` 下的 DMG。
2. 将 `Electron Update Learning.app` 拖到 Applications。
3. 拷贝完成后推出 DMG。
4. 从 Applications 启动应用，避免从只读 DMG 中进行更新。

本次是未签名学习包。如果 macOS 阻止启动，使用系统针对该应用提供的“仍要打开”入口。

这里启动的是包内编译代码，不依赖 Vite 开发服务器。`npm run dev` 与 `npm start` 用于开发运行，不能代替安装包升级验证。

## 五、第四步：检查更新，确认 1.0.0 是最新版本

菜单中确认“当前客户端：1.0.0”，再点击“1. 检查并选择下载”。你已确认显示“已经是最新版本”。

### 5.1 菜单如何进入服务

`bootstrap.ts` 在应用就绪后装配：

```ts
new UpdateService().start()
```

`start()` 注册更新器事件并创建原生菜单。菜单入口：

```ts
click: () => { void this.checkAndDownload() }
```

这里直接运行在 Main 主进程，没有经过 React、Preload 或 IPC。`void` 表示菜单回调不等待 Promise；异步函数内部处理错误。

`checkAndDownload()` 先检查 `busy`、`downloaded` 和 `app.isPackaged`：阻止重复任务、已下载后的重复检查，以及开发模式误用。

### 5.2 checkForUpdates 怎么知道请求地址

关键调用：

```ts
const result = await autoUpdater.checkForUpdates()
```

这里的 autoUpdater 来自 `electron-updater`，不是 Electron 内置的同名导出。

打包时，builder 根据 `publish` 配置生成包内文件：

```text
Electron Update Learning.app/
└── Contents/Resources/app-update.yml
```

内容类似：

```yaml
provider: generic
url: http://127.0.0.1:8088
updaterCacheDirName: electron-multi-tab-updater
```

更新器在生产环境读取 `process.resourcesPath` 下的 `app-update.yml`，获得服务器地址；再根据平台和默认 latest 通道选择清单。

| 平台 | 默认清单文件 |
|---|---|
| macOS | latest-mac.yml |
| Windows | latest.yml |
| Linux | latest-linux.yml |

本例组合为：

```text
http://127.0.0.1:8088 + latest-mac.yml
→ http://127.0.0.1:8088/latest-mac.yml
```

实际请求可能带防缓存查询参数，不影响文件选择。

请区分三个配置文件：

| 文件 | 所在位置 | 作用 |
|---|---|---|
| electron-builder.yml | 源码仓库 | 指导构建，声明更新地址 |
| app-update.yml | 已安装应用内部 | 告诉运行时更新器去哪检查 |
| latest-mac.yml | 更新服务器 | 告诉客户端最新版本、下载地址与校验值 |

修改源码里的 builder 配置，不会改变已安装应用的配置；需要重新打包才能写入新的地址。

### 5.3 为什么显示已经是最新版本

更新器使用语义化版本规则比较本地版本与清单版本。此时：

```text
本地 app.getVersion() = 1.0.0
服务器 version       = 1.0.0
→ 没有更新
```

库发出 `update-not-available` 事件，服务执行 `setStatus('已经是最新版本')`，重新生成菜单。`result.isUpdateAvailable` 为 false，函数直接结束，不下载 ZIP。

## 六、第五步：构建并发布 1.0.1

保持 1.0.0 客户端和服务器运行，在另一个终端执行：

```bash
npm run release:demo -- 1.0.1 --unsigned
npm run publish:demo -- 1.0.1
curl http://127.0.0.1:8088/latest-mac.yml
```

构建过程与旧版相同，但产物版本变为 1.0.1，输出到 `release/1.0.1/`。发布后清单变成 1.0.1；服务器每次请求读取磁盘文件，因此无需重启。

清单的关键字段示意如下，真实值由 builder 生成：

```yaml
version: 1.0.1
files:
  - url: Electron Update Learning-1.0.1-arm64-mac.zip
    sha512: <构建工具生成的校验值>
    size: <文件字节数>
```

`url` 指定文件位置，`size` 是大小，`sha512` 用于校验下载内容是否与清单一致。哈希与代码签名承担不同职责，不能用哈希校验代替代码签名。

不要手动安装新版 DMG；此时要让旧客户端通过更新器发现和获取新版。

## 七、第六步：旧客户端发现新版并下载

回到 1.0.0 客户端，再点“1. 检查并选择下载”。

```text
本地版本 1.0.0 < 服务器版本 1.0.1
→ update-available
→ result.isUpdateAvailable = true
→ 弹窗询问下载
```

服务设置：

```ts
autoUpdater.autoDownload = false
```

所以检查只读取清单。点击“下载”，对话框返回第一个按钮索引 0，服务才调用：

```ts
if (response === 0) await autoUpdater.downloadUpdate()
```

更新器将清单里的相对 ZIP 文件名与服务器地址组合，下载对应文件。它也可能复用之前已下载的缓存，因此重复实验不一定重新传输整个 ZIP。

下载过程中 `download-progress` 更新菜单百分比；下载和完整性校验完成后，`update-downloaded` 把 `downloaded` 设置为 true，并启用安装菜单。

你已确认看到：

```text
1.0.1 已下载并通过文件完整性校验，等待安装
```

此时新版文件已准备好，但当前进程仍然执行旧代码，菜单当前客户端版本仍应是 1.0.0。

## 八、第七步：点击重启安装，理解签名卡点

保存需要保留的内容，点击“2. 重启并安装”，再确认“重启安装”。服务执行：

```ts
autoUpdater.quitAndInstall()
```

本例设置了：

```ts
autoUpdater.autoInstallOnAppQuit = false
```

普通退出不会自动安装。在当前 electron-updater 6.8.9 的 macOS 实现里，手动模式先完成 ZIP 下载并发出 `update-downloaded`；调用 `quitAndInstall()` 后，才触发 Electron 内置更新器与 Squirrel 的原生准备，包括代码签名验证。

原生准备通过后，旧应用退出，更新程序替换应用，再启动新版本。文件下载完成不意味着这一过程已完成。

当前两个版本未签名。此前示例验证中，安装阶段实际出现：

```text
Code signature ... did not pass validation
代码不含资源，但签名指示这些资源必须存在
```

应用仍为 1.0.0。此次你自己的安装结果尚未反馈，应以实际菜单状态和错误为准。

`--unsigned` 只是关闭构建签名，不会关闭原生更新器的签名要求。以后具备签名身份时，使用同一个 Developer ID 身份重新构建两个版本，不加 `--unsigned`，重新安装签名的 1.0.0 后重复实验。脚本此时启用 `forceCodeSigning`，缺少身份应让构建失败；对外分发还需配置公证等发行条件。

真正安装成功的验收条件：重新启动后版本变为 1.0.1，页面与独立窗口正常，再检查显示“已经是最新版本”。

## 九、将运行步骤与代码一一对应

| 实际操作 | 代码或配置 | 结果 |
|---|---|---|
| 构建 1.0.0 | release-demo + builder 配置 | 生成旧版完整应用和清单 |
| 发布 1.0.0 | publish-demo | 服务器目录提供旧版清单 |
| 启动服务器 | update-server | HTTP 可访问清单和 ZIP |
| 安装启动 | DMG 中的 app | 运行包内 1.0.0 代码 |
| 检查同版本 | checkForUpdates | 不下载，显示最新版本 |
| 构建发布 1.0.1 | 两个构建/发布脚本 | 清单和新文件对外可用 |
| 再次检查 | checkForUpdates | 比较版本，发现 1.0.1 |
| 点击下载 | downloadUpdate | 下载或复用缓存，并校验 |
| 点击安装 | quitAndInstall | 原生准备、签名验证、退出替换 |

```text
检查：包内 app-update.yml → 服务器 latest-mac.yml → 比较版本
下载：清单中的 ZIP 地址 → 下载/缓存 → 完整性校验
安装：原生更新准备 → 签名验证 → 退出旧应用 → 替换 → 启动新版
```

## 十、阅读源码的建议顺序

1. `scripts/release-demo.mjs`：理解版本参数与编译、打包的区别。
2. `electron-builder.yml`：理解包的身份、内容、更新地址和产物类型。
3. `scripts/publish-demo.mjs`：理解清单为什么最后发布。
4. `scripts/update-server.mjs`：理解 URL 如何对应磁盘文件。
5. `UpdateService.ts` 的 start、renderMenu、checkAndDownload、install：对应客户端每次点击。

实验结束后退出客户端，在服务器终端按 Ctrl+C 停止服务。编译目录是 `dist/`、`dist-electron/`，分发产物是 `release/`，服务器文件是 `update-server/`；这些均为生成文件，源码和脚本用于下次重建。

参考文档：[electron-builder 稳定版自动更新](https://www.electron.build/v26/docs/features/auto-update/)、[Electron autoUpdater](https://www.electronjs.org/docs/latest/api/auto-updater)。本文的手动安装时序还对照了项目实际安装的 `node_modules/electron-updater/out/MacUpdater.js`。
